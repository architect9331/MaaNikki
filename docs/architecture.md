## 导航

| 模块 | 职责与约定 |
| --- | --- |
| `agent/navigation/frames.py` | 校验 1280×720 框架截图，转换到 1920×1080 识别基准，统一小地图裁切坐标。游戏外截图需另外处理窗口边框与缩放。 |
| `agent/navigation/matching.py` | 地图相关匹配、候选有效覆盖率、缺图边界排除、峰值和背景对齐。地图匹配调用此模块。 |
| `agent/navigation/camera.py` | 在已知地图背景上提取视角光锥方向，排除缺图产生的假边缘，返回方向和置信度。 |
| `agent/navigation/heading.py` | 提取小地图角色箭头，以已发送转向输入维护镜头预期；角色方向与镜头方向分别处理。 |
| `agent/navigation/vision.py` | `Locator` 统一选择灰度、边缘及光锥外候选，检查位移连续性，维护可信位置历史，返回 `Pose`。 |
| `agent/navigation/engine.py` | 转向、移动、松键、停稳复核、场景恢复和路线衔接。消费定位结果，不另写一套定位评分规则。 |
| `agent/navigation/session.py` | 应用通过 `create_navigator` 创建导航器，统一绑定主界面检查、行走状态、任务动作和大地图恢复。日常、路线测试和捕虫靠近共用。 |
| `agent/navigation/teleport.py` | 大地图定位、传送和角色中心复核。图像相关计算使用共用地图匹配器。 |
| `agent/navigation/geometry.py` | 点到路线段的投影与距离；路线匹配和恢复共用，传送点之间的间隔不视为可行走路线段。 |
| `agent/navigation/daily_route.py` | 到点任务动作、采集数量与分支策略。每日限额和全点位调查的差异保留在任务层。 |

调用关系为：任务 → `session` → `engine` → `Locator` → `matching` / `camera` / `frames`。`Teleporter` 同样复用 `matching`。核心 `Navigator` 保留可注入接口，应用入口统一在 `session` 中组装依赖。

### 缺图与可信位置

导航参考图的零像素表示未采集地形。匹配器按每个候选的有效地形计算相关性，排除缺图及其边界，最低覆盖率为选中区域的 60%。这项规则对普通灰度、地形边缘、光锥外、大地图及视角背景对齐统一生效，调用方无需另行开启。UI 模板中的黑色可以是真实图案，因此 UI 模板识别仍使用自己的识别接口。

视角识别在模糊和极坐标变换前扩大缺图边界遮罩，避免填充边缘产生假光锥。缺图处可使用原地连续两帧确认方向后记录的光锥外地形，仅补充视角背景；位置匹配仍使用原参考地图。局部背景随可信坐标平移对齐，平移超过 24 个参考像素、超过 30 秒或定位重置时清除。首次记录要求两侧光锥边缘都有足够的径向支持；缺图且没有临时背景时采用更高的边缘支持要求，避免短地形线以高置信度成为假方向。

完整背景与缺图背景均检查两侧光锥边缘的径向覆盖和内外半段分布，先排除局部地形弧线，再比较方向候选的峰值。原有 20% 径向支持要求统一应用于完整背景；使用临时背景补图时保留 10% 要求。峰值突出程度表示候选之间的差异，不能替代边缘质量。日志记录候选强度、径向覆盖及最终选用项，便于区分缺少证据与候选歧义。

镜头预期来自上一次可信方向和本次实际发送的鼠标位移，转角误差预算沿用校准允许的约三分之一比例误差，并留 8° 的识别与镜头过渡余量；它只触发复核，不强制沿用旧方向。角色箭头通过中心青色轮廓与箭头几何提取；连续前进及最近转向后均经过 0.25 秒对齐预算时，可独立佐证光锥。站立时箭头仍表示角色旧朝向，不能用于测量镜头转角。箭头形状不明确时跳过该证据；这些预算需随用户实跑日志评估，不增加前进按键时长。

`Pose.position_reliable` 表示位置能否用于导航；`heading` 为 `None` 表示无法按当前方向移动。被拒绝的位置可能保留上一次坐标作为恢复锚点，调用方必须检查可信状态。通过 `Locator.accept()` 提交已确认位置，通过 `reset()` 重置连续性；大地图复核后的试读使用 `commit=False`，确认稳定后才提交。

位置复核时连续读数相近只表示候选稳定。候选距中断前可信位置超过 4 个地图单位时，必须先用大地图独立复核，再接受新位置；等待时间增长不能替代这项检查。复核后投影回当前路线段，保持点位索引，不按最近历史点回退，也不以离端点较远判定长路段中部偏航。日志中的 `scene_anchor_conflict` 记录突变，`position_confirmed.verification` 标明复核来源。

主界面暂不可用时，共用恢复入口通过「深水警告」标题模板和「复活」按钮 OCR 确认落水页面，松开导航按键后点击复活并等待主界面。复活后以 `NavigationStuckError` 交还路线调用方，星海结晶日常沿用从传送点重试的次数限制；路线合集将本条记为失败并从下一条起点继续。合集的失败续跑先恢复主界面，恢复失败则结束本轮。`deep_water_revive`、`deep_water_recovered`、`collection_recovery` 记录相应结果。

地图差异写在 `resource/navigation/maps.json`，不在算法里按地图名称分支。`position_score_floor` 默认 0.55；`miraland` 的 `null` 保留原有不设最终分数下限的策略，缺图排除及位移连续性检查仍然生效。新增地图应先沿用默认规则。

导航日志记录实际尝试方法、选用结果、恢复原因、松键耗时、停稳复核与采集结果；路线测试另存失败和到点截图。

`jump_transition` 记录起跳、第一次松键、第二次按下与松键之间的实际间隔，以及切换步行、到点、脱困结束或导航中断导致的取消。`air` 表示二次按键流程已发送，游戏内悬浮是否生效仍需画面确认；`jump_cancel_input` 单独记录主动取消悬浮的按键。

前进规划使用固定 0.06 秒松键提前量，默认近点与远点转向容差为 3°、5°。星海基础容差为 3°、4°；`heading_position_slack` 配置 0.1 个地图单位的近点位置波动预算，取预算与到点半径四分之一的较小值换算角度，近点方向容差最高放宽至 5°。转向后的前进检查按最新距离重算容差，到点半径和停稳复核保持独立。

星海普通半径不超过 1 的途经点按 0.75 倍判定到达；`transit_pass_radius_scale` 保留 0.8 倍的经过余量。进入较小半径即可通过；只进入较大余量时，须由连续位置确认实际经过目标在移动线段上的投影点，避免仅靠近就提前接受较大半径。转向前后共用该判定，经过后可继续下一点。交互、恢复和最终到点，以及显式放宽的巨陨星路点保持原半径。日志中的 `radius` 和 `pass_radius` 分别记录到达与经过判定半径。

方向超出转向预期、光锥证据不足，或连续三次转向后仍无法前进时，先松键并在当前小地图复核方向。确认采用持续 0.2 秒、角度范围小于 5° 的稳定区间，覆盖现有 0.15 秒镜头过渡时间；任一读数无效或超出范围即重新开始计时，2 秒内未取得稳定区间则停止。复核可接受用户手动转动后的新方向；超出输入预期的反馈不用于学习灵敏度。方向复核自身不打开大地图，连续复核上限沿用三次预算，有效前进或进入新点位后清零。`heading_recheck_started`、`heading_confirmed` 与 `position_recheck_started` 分别记录方向和位置复核；异常方向首次出现时保存可信帧、异常帧及候选数据。导航共用缺图排除、可信位置与路线段恢复、转向过冲抑制及诊断记录；新点位通过路线工具由用户实跑确认后用于日常任务。

### 动作朝向

导航连续前进，小角度修正沿用边走边转，普通移动与跳跃分别估速。前进截止时间以目标点中心为准，扣除截图后已前进时间和松键余量；截图采集时刻取请求区间中点，识别期间的静止时间单独计量。临近截止时间先松键，再进行耗时识别。

大角度转向与校准时停止前进，校准结果波动时补采样并平滑更新比例。任务点、终点和路线接入点在停下后复核。捕虫复用路线校准比例，对准至 3° 内后前进；新路线、传送和暂停恢复后重新校准。

`Navigator.face_heading(heading)` 负责停车、将镜头转到指定角度，再调用 `ForegroundInput.face_camera()` 对齐角色。后者短按 Ctrl＋配置的前进键 0.08 秒，先松前进键再松 Ctrl，等待 0.4 秒让转身动作完成；前台中断时释放按键，不恢复这次短按。该动作以利用移动起步前的转身阶段为目的，实际是否无位移由游戏内实跑确认。

钓鱼、钓星点通过 `params.facing_heading` 保存水面方向（0° 为北，顺时针增加），不使用抵达时最后一次位置修正的朝向。现有角度依据路线的入场方向设置；新增点位应记录并验证水面方向。家园在进入采星、隐藏小地图之前完成对齐；当前位置主动钓鱼沿用当前镜头方向。接管已开始的钓鱼不执行转身。`character_facing` 记录目标方向、镜头校验、短按时长及导航能测得的位置变化，角色本身的朝向仍需实跑观察。

### 星光结晶选线

摇铃后分辨地图内标记与边缘提示，优先点击边缘提示移动视野，取得地图内坐标；提示被控件遮挡时切换备用视野。单轮定位上限 20 秒，标记稳定消失或超时后重新摇铃。

选线计算每个结晶到路线折线的距离，按最远距离、平均距离、固定路线顺序排序，要求所有结晶距路线小于 25 个地图单位。选定后沿用当前地图寻找起点传送点，再完整执行路线。定位事件、候选距离和标记数量保存在 `logs/navigation/*-starsea.json`。

## 任务、页面与输入

| 模块 | 职责与约定 |
| --- | --- |
| `agent/daily/runtime.py` | 框架动作、截图、任务参数和输入所有权；嵌套流程沿用 `input_guard()`。 |
| `agent/game_view.py` | 游戏截图统一采用 1280×720 基准；尺寸校验供日常、祝福闪光、自定义识别和导航共用，启动器截图不经过此入口。 |
| `agent/diagnostics.py` | 共用失败现场、近期识别记录和截图保存；完整画面只遮 UID，局部截图在遮罩后按显式 ROI 裁切。 |
| `agent/daily/ui.py` | 页面入口、局部特征确认、等待和页面恢复。页面跳转通过现有 `enter_page` 等入口。 |
| `agent/client_config.py` | 解析当前控制器，优先使用提交任务时的 `PI_CONTROLLER`，缺省时读取保存的实例；统一判断前台输入能力。 |
| `agent/daily/settings.py` | 任务设置及控制器能力的业务入口，不重新解释控制器格式。 |
| `agent/navigation/controller.py` | 前台输入、焦点暂停和按键释放。任务不得绕过输入所有权自行维护另一套按键状态。 |

页面动作继续遵循仓库约定：通过 `Runtime.action` 或 `nikki.ui_click` 发起点击，入口配置 `ready` 和 `source`，只重试可安全重复的进入操作。奖励领取、周期完成确认、采集限额等属于业务策略，不因共用页面或导航模块而合并。

`Runtime` 的完整截图及自定义识别回调校验画面尺寸；首次输入前若当前回调尚无已校验画面，则先截图。供 OCR 使用的局部图像不按完整截图校验。校验只读取图像尺寸，不增加逐帧识别。发现非 1280×720 框架截图时，由 `ForegroundSession` 记录实际尺寸及 16:9 设置提示，释放输入并停止整批任务，恢复流程也不得继续点击。实际游戏可使用其他 16:9 分辨率，由框架等比缩放至基准；不拉伸或裁切非 16:9 画面。

### 常驻调度与截图

`agent/scheduling.py` 的 `PeriodicSchedule` 使用同一个墙钟起点安排周期检查，错过的周期直接跳过，不积压补跑。开荒辅助保留拾取 100 毫秒、清洁 300 毫秒、对白 500 毫秒及原有命中冷却；10 毫秒内相邻的到期检查共用一帧。钓鱼仍独占输入，清洁跳过后仍等待提示消失。拾取识别区域、模板及阈值维持原有规则。

`Runtime.capture_at(deadline, available=...)` 是常驻检查的截图入口，时间戳使用 `time.monotonic()` 墙钟。默认在检查前 30 毫秒提交 MaaFramework 异步截图，将截图等待与检查前的空档重叠；一次只持有一个作业，同一线程等待并读取结果。按键结束后才安排下一次截图，停止、窗口不可用或焦点代际变化时放弃结果；预取期间唤醒延迟超过 100 毫秒时重新截图。作业退出前等待完成，不遗留截图队列。`Runtime.capture()` 继续立即请求新帧，导航、页面确认及日常任务不自动启用预取。

`logs/performance/` 记录 `capture.post`、`capture.overlap_idle`、`capture.prefetched`、`capture.discarded`、`assist.decisions` 和 `assist.checks_due`。预取时 `capture.wait` 仅表示到检查时间后剩余的等待，`capture` 包含重叠空档；比较性能时分别核对等待时间、底层截图耗时和 CPU 开销。`agent_cpu_ms` 是本次动作期间整个 Agent 进程的累计 CPU 时间，不包含客户端进程及 GPU 开销。比较时应结合运行时长、截图次数与相同功能开关下的实跑表现。

## 状态与日志

失败现场统一调用 `Runtime.diagnostic(stage, reason, image=..., details=...)`，优先在页面恢复、关闭地图或任务清理之前保存。共用会话保留一张最近观察帧和最多 24 条识别/输入摘要，不增加正常循环中的截图请求或文件写入；回调退出释放帧引用。保存内容包含阶段、原因、画面尺寸、帧龄、焦点代际、OCR 原文、模板阈值及匹配分数。无可用画面时明确标注 `image_status`，不可用后续恢复画面冒充失败原帧。操作返回失败或意外异常由注册层兜底，兜底时机明确标为 `after_action_return`。

现场图与 JSON 放在 `debug/on_error`，结构化摘要同时追加到 `debug/messages`，沿用现有 Sentry 开关及任务起止边界上传。客户端优先收集 Agent 业务消息，避免框架的大量调试日志先耗尽日志预算。已有大小与采样限制仍生效。

`resource/data/diagnostic_images.json` 是 Python 截图与客户端导出/上报共用的遮罩定义：1280×720 基准下只遮左下角 `[0,700,200,20]`，其他完整画幅按高度等比换算。完整现场不裁底部；卡片、提示框、小地图等局部图按指定 ROI 裁切，不另猜 UID 位置。所有 Agent 图像写入经过 `diagnostics.save_image`；启动器与已裁好的库存局部图显式标为局部图。MaaFramework 自行生成的完整 PNG 在导出和 Sentry 打包时应用相同遮罩，不覆盖框架原文件，也不尝试补回历史截图已经裁掉的内容。

祝福闪光提示框字段由 `agent/collection/details.py` 统一解析，库存扫描与整理共用。名称和等级沿用调用方的 OCR 门槛；颜色可单独采用 0.70 门槛，但低于普通门槛的行须完整匹配合法颜色词（可带圆点前缀），并通过提示框位置、套装颜色及等级约束。整理流程的严格识别仍使用 0.90，颜色降门槛的结果走两次 OCR 一致且字段像素稳定的确认路径，不用于单次识别快速放行。

`agent/file_io.py` 提供唯一的原子 JSON 快照写入：UTF-8 编码、拒绝非有限数值、同目录唯一临时文件、刷盘后替换。账号状态、祝福闪光报告、启动记录、日常诊断及性能快照使用此入口；它不依赖任何业务模块。

`agent/account_state.py` 继续负责账号标识、周期与完成状态，`agent/collection/storage.py` 负责祝福闪光业务数据。状态持久化失败应由上层明确处理；可选诊断写入失败不能覆盖原任务结果。JSONL 是追加事件流，保留追加写入方式，与完整快照区分。

巨陨星观测保存在同一账号状态文件的可选 `observations.giant_meteor` 中，包含 `game_day`、`outcome`（`found` / `not_found` / `unconfirmed`）、`checked_at` 和地图提示原文，沿用 schema 2。日期与周期任务共用中国时区 04:00 刷新规则；普通日提示区域可以为空，只有确认地图页面后连续两次未识别到提示才记录未发现。一次已确认的发现会保留至当天结束，后续未发现或未确认不会抹去它。客户端沿用账号状态轮询，过期结果显示未检测；庆祝通知在同一客户端会话的同一游戏日只展示一次。

`client/src/utils/blessingProgress.ts` 统一计算五星收集范围和已确认颜色，供进度页与主界面百分比共用；无完整记录时显示空缺标记，未确认操作继续标注为上次确认记录。
## 页面与识别调度

页面入口使用 `GameUI.enter_page`，等待使用 `GameUI.wait_page`。通常连续两次识别到局部特征后确认到达；需要等待图像稳定时显式配置 `stable=True` 与 `roi`。

Pipeline 的 `custom_action_param` 配置 `ready`、`source`，可用 `ready_timeout` 指定秒数。入口默认最多尝试三次，按来源页和目标页状态决定等待或恢复。领取、兑换、点赞等提交操作按确认结果推进。

Esc 菜单的挖掘、星绘图册、奇迹之冠入口共用 `find_menu_entry`。页面识别与恢复记录位于 `logs/navigation/*-page.json`。

同一轮只读判断使用 `Runtime.observe()` 复用截图，最长 250 毫秒；输入、等待、移开鼠标或显式 `capture()` 会使观察帧失效。积分读取共用 `DailyRun.open_score_page()`：页面特征确认后等待 1.5 秒，最多读取三次，每次间隔 0.4 秒，采用连续两次相同的积分。

朝夕升级心愿通过 `collection/daily_upgrade.py` 复用 `UpgradeUI`，以 `once=True` 确认一次等级或经验增长后结束。对象按五星、四星、三星排序，满级上限取图鉴；有完整顺序基准时复用新增区核对和局部定位，更新原队列及五星收藏，无基准时直接读取普通列表。`run_state.PendingReview` 保存待补升级卡；同轮全收集由其原升级流程完成，普通刷取后只复读该卡并按需升级一次。幻境入口记录实际模式，失败的幻境结算只复核积分与领奖。

模板由 `agent/vision.py` 准备，解码和预处理缓存分别上限 64、128 项，按路径、修改时间、大小和处理参数区分。`logs/performance/*.json` 记录截图、识别、模板、输入、等待及缓存统计；持续辅助每 60 秒更新报告，`p95_upper_ms` 为直方图估计上界。

## 开发模式

在「设置 → 调试设置」开启开发模式，可添加路线测试和朝夕、星海子任务。工具执行所选任务动作，幻境会消耗活跃能量，家园流程会使用钓星次数。

| 路线工具模式 | 用途 |
| --- | --- |
| 路线导航 | 执行移动、跳跃、传送、等待 |
| 家园完整流程 | 按家园路线执行钓星、下落攻击等动作，可选择能力方案 |
| 漂流瓶全点位 | 对所选路线逐点尝试拾取并跑完全程 |
| 大小地图定位对照 | 在星梦群屿·海滩起点及四个点位记录大小地图位置、差值与截图 |

本地路线 JSON 可来自 `resource/routes/daily/`、路线工坊或自行编辑。缺少起始传送点时，先将角色移到首个点位附近。

在「路线导航」中选择 `resource/routes/collections/starsea_all.json`，可连续运行 23 条星海路线。合集启动时固定各路线快照，每条重新传送并独立计时；单条导航失败后记录现场，继续下一条，手动停止、程序接口异常或松键失败时结束合集。导航模式保留跳跃和急坠，跳过拍照、交付等任务交互。

合集记录位于 `logs/navigation/*-route-collection/`：根目录 `collection.json` 保存清单，`result.json` 汇总各路线结果与耗时；`route-01/` 等子目录保存路线快照、事件和失败截图。`waypoint` 事件记录到点坐标、实际半径和越点判定，`navigation_profile` 记录本轮地图容差。

漂流瓶路线 1 为 `xinghai_bottle.json`（无界枢纽，6 点），路线 2 为 `xinghai_bottle_2.json`（星梦群屿·海滩，4 点）。正式任务按首条路线的 `fallback_routes` 顺序继续查找，达到当天要求后结束。路线工具逐点记录结果。

路线 1 的旧坐标来自旧版缩放小地图定位。现用本路线 10 张已录制截图分别换算旧采样与原生居中采样坐标，按各点差值的中位数迁移 6 个拾取点，起点取全部样本差值中位数；拾取半径仍为 0.4。原位置、逐点偏移与截图运行批次保存在路线的 `coordinate_migration`，后续修改以当前坐标为基准。

路线 2 的 P02、P04 取可拾取范围两端的中点，参考半径约为 0.65、0.79，路线到达半径为 0.4；采样位置与来源保存在 `params.sample_position`、`params.pickup_range_reference`。采集地图坐标时，将地图放大至最大、保持角色居中，裁去窗口标题栏和边框后核对 UI 对齐。

## 祝福闪光数据与诊断

### 仓库基准与增量定位

完整读取以获得时间倒序记录三个部位的观察顺序、唯一编号、队列优先级、位置提示和满级锁定参照。数量读取先识别堆叠标记，再遮罩、放大角标区域做 OCR，采用两次一致的有效结果。锁定项每格一件；三个部位的总数与仓库容量核对后保存基准。

底部渐隐格在滚动至清晰区域后读取。连续两次向下滚动确认位置相同时，扩大到末行完整格。解锁导致叠放合并时，对发生变化的部位复核顺序。

锁按钮按两种状态分别组合证据：完整二值图标达到原有匹配门槛、且与锁扣部分的候选方向一致时采用其形状判定；完整图标共用锁身，不再要求固定分差。灰度和独立锁扣分支保留原有质量及分差要求，明确分支冲突时保留未知。未锁定以形状为依据；锁定还须四个分区共同确认不透明黄色填充。透明按钮背后的白色服饰可能填补开口，因此闭合形状单独不足以确认锁定；服饰恰好同时模拟闭锁形状与黄色填充时仍可能误判。操作前后沿用连续两帧确认、一次提交锁操作；确认失败时保存各帧评分与判定，正常流程不增加截图或等待。

翻页优先以列表下半屏卡片匹配位移；轮廓不足或有效匹配不足时，复用同一对截图，扩大到当前页其余完整卡片。灰度候选难以区分时，`scroll_color.py` 对满足原有形状分数及差距范围的独立峰比较图标主体颜色：沿用 `IconMatcher.chroma` 的亮度归一化、颜色分数 0.80 和差距 0.025，以局部亮纹理和色度能量加权，避开星级、等级、数量和锁标。这些已有颜色标准在截图间比较中的适用性仍需实跑日志评估；选中染色或透明背景变化可能使颜色证据不足，颜色近似的重复副本也继续保留歧义。扩展参照与颜色辅助均保留三列位移一致及多数有效匹配的要求，不额外截图或滚动。最终无法确认时，失败诊断包含灰度与颜色候选分数、竞争位移与滚动前后画面。

仓库读取在前台切回后局部恢复：复用当前页截图，核对部位、获得时间倒序、容量、格子图像和滚动条，再重新读取中断的格子。翻页中断通过三列重叠图像及等级、数量、锁标确认实际位移；已提交的锁操作只核对结果，未提交的输入重新确认对象后执行。恢复仅针对当前页，每次中断最多恢复一次；列表位置、叠放变化或输入结果无法确认时保存记录并退出。正常扫描沿用已有截图。

增量读取顶部新增区域，匹配最多三个按旧顺序排列的唯一锁定参照后接上旧记录。缺少唯一参照的部位在本轮完整读取一次；新增前缀上限 24 页。

升级返回后优先检查当前可见区域，再按位置提示局部查找，最多六页。操作前核对名称、等级、选中状态及锁按钮。队列项的移除依据两侧参照或列表端点之间的完整观察；未完成对象与参照异常时保留进度，交由用户重新读取仓库。

图鉴外名称以完整星级提示条和两次一致、稳定的字段识别记录为 `catalog_unknown`。自动处理范围取自本地图鉴；图鉴外物品的保留由游戏锁定状态控制。全收集先执行刷取后的四星及以下分解，再核对新增区域、升级五星。

### 账号状态字段

账号文件为 `config/accounts/CN/<UID>.json`，外层 `schema_version: 3`，包含 `uid`、`region`、`tasks`、`blessing`、`observations`、`resonance`。Python 与 Rust 通过 `config/accounts/store.lock` 互斥并原子替换文件，更新时保留其他模块字段。

任务从左下角 UID 标签确认游戏角色，绑定本次任务的读写目标；写入前复核可见 UID，前台变化后身份未确认时保留原存档。周期任务由游戏端绑定 UID 后判断完成状态，前端只显示已记录状态。美鸭梨登录仅决定共鸣数据归属，不切换当前游戏角色索引。

`index.json` 保存最近确认的游戏账号和旧数据迁移归属。旧版 `account_state.json` 的无 UID 任务、仓库和观测数据，在首次游戏 UID 确认时绑定到该角色；迁移归属先预留，账号文件保存后再发布活动索引，中断后仅原 UID 可恢复迁移。旧共鸣记录依其自带 UID 迁移，所有旧文件保留。

`blessing.inventory` 保存最近一次完整数量记录，`blessing.last_scan` 保存最新处理状态；嵌套库存快照保留 `schema_version: 1`。

| 字段 | 内容 |
| --- | --- |
| `items` | 名称、部位、星级、颜色、等级、经验、数量和识别标记；未知颜色记为 `null` |
| `locks` | 已核实的锁定数量，全收集过程确认每种收藏至少一件 |
| `protected_inventory` / `inventory_evidence` | 图鉴外受保护三星的兼容标记与星级、锁定识别依据 |
| `catalog_unknown` | 图鉴外名称标记，结合 `inventory_evidence` 记录实测星级 |
| `excluded_items` | 兼容旧特殊物品列表，读取时合并到 `items`，新写入为空列表 |
| `scan` / `unresolved` | 遍历、容量、数量完整性及识别待处理项 |
| `organization` | 完整基准、排序、部位顺序、唯一编号、位置提示、队列优先级、未完成对象和待确认操作 |
| `pursuit` | 已保护颜色、缺色、副本、升级结果与资源状态；`changes` 记录本轮前后数量及颜色变化 |
| `record` / `created` / `catalog_version` | 来源、更新时间、证据目录和图鉴版本 |

`organization.slots.count` 与 `count_evidence` 表示观察时的数量和依据。当前数量的可用状态由 `items` 和 `scan.quantity_state` 表示。刷取、升级和锁定提交前写入待确认记录，确认后更新状态；升级结束按已确认的锁定满级颜色保存进度。

### 操作证据

`logs/blessing-lock/<时间>/locking.json` 记录仓库读取与锁定；`logs/blessing-pursuit/<时间>/pursuit.json` 记录刷取和升级，同目录保存状态快照。

逐格诊断保存 `card_<编号>.png`、`card_<编号>_badge.png`、`card_<编号>_lock.png` 和同编号 JSON，分别对应原始卡片、数量角标、锁标与识别字段。数量 OCR 另存遮罩数字图和识别结果，失败格及触底时保存完整列表截图。

### 错误上报

Sentry 配置取自 `interface.json` 的 `telemetry.sentry`。失败诊断收集本轮 `debug/` 日志片段和新现场图：日志总量最多 1 MiB，单文件最多 512 KiB，截图压缩包最多 5 MiB。运行追踪按 10% 采样，任务失败事件独立上报，设备通过哈希标识关联。

调试与开发构建默认关闭上报。原生崩溃的源码行号取决于符号上传配置；导航记录通过客户端导出日志分享。

## 修改共用逻辑时

1. 先定位行为所属模块，再搜索调用点；检查日常任务、开发模式、局部靠近、传送与恢复是否共用同一入口。
2. 修改返回值或诊断结构时，同步更新消费者。旧工具需要的接口可保留薄转发层，不复制算法；例如 `Locator.match` 转发到 `match_map`。
3. 将地形、窗口和输入规则放在基础层，将任务数量、周期与完成条件留在业务层。说明新增策略的适用范围。
4. 按[构建指南](../BUILDING.md)完成静态检查；游戏内效果由用户实跑验证。交付时列明受影响入口和需要复核的行为。
